# Заметки для защиты

## Цель приложения

Приложение демонстрирует MVP сервиса доставки еды для университета. Пользователь регистрируется или входит через Firebase, просматривает рестораны и меню, добавляет позиции в корзину, оформляет заказ с адресом доставки, затем видит историю заказов и детали конкретного заказа.

## Клиент-серверная архитектура

Проект разделен на две независимые части:

- `android/` - мобильный клиент.
- `server/` - backend API.

Android-приложение отвечает за интерфейс, локальную корзину и получение Firebase ID token. Backend отвечает за бизнес-логику заказов, хранение данных в PostgreSQL и проверку токена.

## Ktor Backend

Backend написан на Kotlin с Ktor. Основные маршруты:

- `GET /restaurants` - список ресторанов.
- `GET /restaurants/{id}/menu` - меню ресторана.
- `POST /me/sync` - синхронизация Firebase-пользователя с backend.
- `POST /orders` - создание заказа.
- `GET /orders/my` - заказы текущего пользователя.
- `GET /orders/{id}` - детали заказа.

Логика вынесена в use cases, маршруты только принимают HTTP-запросы, валидируют входные данные и возвращают DTO.

## Retrofit Client

Android использует Retrofit для вызова Ktor API. `AuthInterceptor` добавляет заголовок `Authorization: Bearer <Firebase ID token>` к защищенным запросам. DTO из сети преобразуются в domain-модели и сохраняются в Room там, где это нужно для локального состояния.

## Firebase Auth

На клиенте используется Firebase Authentication с Email/Password. После входа или регистрации приложение получает текущего Firebase-пользователя и вызывает `POST /me/sync`, чтобы backend создал или обновил запись пользователя в PostgreSQL.

## Проверка Firebase ID Token На Backend

Backend использует Firebase Admin SDK. Для защищенных endpoint-ов Ktor authentication plugin проверяет Firebase ID token из bearer-заголовка. После проверки backend получает `uid`, email и имя пользователя. Заказы доступны только после синхронизации пользователя через `POST /me/sync`.

## PostgreSQL Neon

Основная база данных - PostgreSQL, можно использовать Neon. Подключение настраивается через переменные окружения:

- `DATABASE_URL`
- `DATABASE_USER`
- `DATABASE_PASSWORD`

Пароли и строки подключения не хранятся в репозитории. Миграции Flyway создают таблицы пользователей, ресторанов, меню, заказов и позиций заказа.

## Room/SQLite

На Android используется Room поверх SQLite. Локально хранятся рестораны, меню, корзина и кеш заказов. Корзина работает локально, а при создании заказа отправляется на backend. После успешного ответа `201 Created` корзина очищается.

## Clean Architecture Layers

В Android-клиенте слои разделены так:

- `presentation` - Compose screens, UI state, ViewModels.
- `domain` - модели, интерфейсы репозиториев, use cases.
- `data` - Retrofit API, Room DAO/entity, реализации репозиториев, мапперы.
- `di` - Hilt-модули.

В backend аналогично разделены маршруты, use cases, модели, репозитории и слой базы данных.

## Тесты

Backend-тесты проверяют health endpoint, auth/sync flow, рестораны и заказы через Ktor test application. Android-тесты проверяют расчет суммы корзины, Room DAO и поведение репозиториев. Команды:

```bash
cd server && ./gradlew test
cd android && ./gradlew test
cd android && ./gradlew build
```

## Demo Script

1. Запустить backend с настроенными переменными Neon и Firebase.
2. Запустить Android-приложение с `google-services.json`.
3. Зарегистрироваться или войти через Firebase.
4. Объяснить, что приложение вызывает `POST /me/sync`.
5. Открыть список ресторанов.
6. Открыть меню ресторана.
7. Добавить блюдо в корзину.
8. Изменить количество.
9. Ввести адрес доставки.
10. Создать заказ и показать успешный переход к деталям.
11. Показать, что корзина очищена.
12. Открыть вкладку Orders и показать созданный заказ со статусом и суммой.
13. Открыть детали заказа и показать список позиций.
14. Открыть Profile, показать email пользователя и выполнить sign out.
